参考PDFから**転用した原則**（設計の着想のみ。飲食店向けの集客施策・自動公開は転用しない）:

- 書く役と確かめる役を分ける（本実装ではコードによる決定的な根拠検査を必須にした）
- 出力は下書き止まり。2回不合格なら止めて人間に知らせる（本実装では Hold 隔離・通知）
- 資料（プロフィール）にない事実は書かない（本実装では `source_ids` のない主張を「要確認」にする）
- 1回の手作業版から段階的に自動化する（本実装では模擬AIで全経路を通してから実APIへ進む）

**転用しないもの**: 毎晩の自動公開、Googleビジネスプロフィール投稿、ライバル店分析、SEO/MEO目的の大量ページ生成。いずれもREALORIAの編集独立性・真正性の原則と合わない。

## 2. 全体構成

```
┌──────────── ブラウザ (PC / スマホ) ────────────┐
│ ホーム / 組織 / 連携図 / AI対話 / ジョブ / 監査 │  ← 自前のJS/CSSのみ。CSPでインライン実行を禁止
└───────────────┬────────────────────────────────┘
                │ HTTP (既定 127.0.0.1:8765)・Bearerトークン
┌───────────────▼──────── realoria_cc (単一プロセス) ─────────────────────┐
│ api.py      ルーティング・入力検証・セキュリティヘッダ・静的配信          │
│ core.py     認証/セッション・ジョブ制御(リース/フェンシング)・緊急停止・情報源 │
│ security.py ロール/人間専用操作/データ区分/外部送信ポリシー               │
│ org.py      6本部・33機能・3委員会・G1〜G5 レジストリ + 整合性検査        │
│ agents.py   役割別エージェント実行・根拠検査(捏造抑制)・ハートビート       │
│ providers.py Provider IF (Mock / OpenAI / Anthropic / Local) + ModelRouter │
│ service.py  Worker×N・Monitor(回収・監査検証・アンカー)・health・backup/restore │
│ audit.py    ハッシュ鎖 + HMAC + 外部アンカー                               │
└──────┬──────────────────────────┬──────────────────────┬───────────────────┘
       │ SQLite (WAL, FULL sync)  │ secrets/audit.key     │ anchors/audit_anchor.jsonl
       ▼                          ▼ (DB外)                ▼ (DB外・追記専用。将来は別媒体)
```

依存ライブラリは **Python 3.11+ 標準ライブラリのみ**（検証環境は 3.13）。

### 技術選定の理由と代替案

| 項目 | 採用 | 理由 | 代替案と移行条件 |
|---|---|---|---|
| 言語 | Python | Windowsで導入しやすい。LLM SDKが揃っている | — |
| DB | SQLite (WAL) | サーバー不要、単一PCでの24時間運用に十分。`BEGIN IMMEDIATE` で書込みを直列化 | 複数ホスト化・同時書込みが多い場合は PostgreSQL（行ロック `SELECT … FOR UPDATE SKIP LOCKED`） |
| API | `http.server` (Threading) | 依存ゼロでサプライチェーンリスクと導入手間を抑えた | FastAPI + uvicorn。OpenAPI自動生成・非同期・入力スキーマ検証が必要になった段階で移行。`core.System` は Web 層と独立しているので差し替えは API 層のみ |
| UI | 素のJS/CSS | CDN不要（オフライン運用・CSP厳格化） | 画面が増えたら Vite + 小規模フレームワーク |
| 常駐 | `serve` 1プロセス（Worker + Monitor 内蔵） | 単純さ優先 | Windows: NSSM またはタスクスケジューラで自動再起動（**未検証**） |

## 3. 主要な不変条件

### 3.1 ジョブ制御（重複防止・停止・復旧）

状態: `queued → running → succeeded | failed | held | paused | cancelled`

| 不変条件 | 実装 |
|---|---|
| 同一ジョブを二重実行しない | `BEGIN IMMEDIATE` 内の `UPDATE … WHERE state='queued'`（行数1のみ成功） |
| 旧所有者の書込みを拒否 | claim ごとに `lease_token` を単調増加、`attempt_id` を発行。finish/heartbeat は (attempt_id, token, 停止世代, 期限) 全一致時のみ |
| 期限切れリースは回収前でも書込み不可 | `_check_lease` が `lease_expires <= now` を拒否 |
| 異常終了後の復旧 | Monitor の `reap()`: 再試行安全かつ回数内 → 再キュー、それ以外 → **Hold 隔離** |
| 安全な再試行 | 指数バックオフ。`retry_safe=0`（副作用あり）は自動再試行しない。ポリシー拒否は再試行しない |
| 緊急停止 | `stop_generation` を進める → 実行中の書込みは全て失効 → 実行中ジョブは Hold。新規受付・claim を停止 |
| 再開 | 人間の admin のみ。監査検証が成功している場合のみ |
| モデルの無断変更防止 | プロバイダ/モデルは受付時に固定。変更は queued/paused の間だけ、人間が実行し監査記録 |

### 3.2 権限分離

- 主体は `human` / `ai` / `system`。AI はパスワードでログインできず、`admin`・`operator`・`approver` ロールを付与できない。
- `HUMAN_ONLY` の操作（Hold解除、モデル変更、再開、利用者管理、バックアップ、承認、情報源登録）は、ロールに関係なく人間以外を拒否する（DBを直接改変してロールを付けても拒否されることをテスト済み）。
- **ここでのロールはシステム操作上の技術的権限であり、REALORIAの正式な組織権限ではない。** 正式権限は照合後に別レイヤーとして実装する。

### 3.3 データ区分と外部送信

| 区分 | 例 | 模擬 | ローカルLLM | 外部AI |
|---|---|---|---|---|
| 0 公開 | 公開済み記事 | 可 | 可 | 設定で許可した場合のみ（既定は不可） |
| 1 内部 | 運営メモ | 可 | 可 | 既定は不可 |
| 2 機密 | 契約・財務 | 可 | 可 | 既定は不可 |
| 3 厳秘 | **未公開取材素材**・人物保護情報 | 可 | 可 | **設定に関係なく常に不可** |

- ジョブの区分は「宣言区分」と「参照資料の区分」の最大値になり、低くすることはできない。
- 利用者の `clearance` を超える区分のジョブ・資料は、一覧にも表示しない。
- 送信内容そのものは監査ログに残さず、SHA-256・文字数・区分・プロバイダ・結果を記録する（本文はジョブ内に保存され、区分で保護される）。

### 3.4 監査保全（3層）

1. DB トリガーで `audit_log` の UPDATE/DELETE を拒否する
2. ハッシュ鎖 + HMAC（鍵は DB 外の `secrets/audit.key`）で改変・欠落・順序入替・鍵を持たない者による再計算を検知する
3. 外部アンカーファイル（追記専用・HMAC付き）で末尾の切り詰めや巻き戻しを検知する。Monitor が監査の進みを見て随時アンカーを書く

監査の追記は業務処理と**同じトランザクション**で行う。監査が書けなければ、その操作も成立しない。検証に失敗すると、監査鎖に追記しない経路で**自動的に安全側へ停止**する。

**限界**: 鍵とアンカーが DB と同じディスク・同じ OS 権限下にあるため、その OS の管理者権限を持つ攻撃者には対抗できない。独立性を高めるには、アンカーを別媒体・別ホスト・WORM ストレージに置き、鍵を Windows DPAPI や HSM に移す必要がある（次工程）。

### 3.5 AIの誤認・捏造の抑制

- システムプロンプトで役割を「調査・比較分析・改善案」に限定し、資料外の推測を禁止する。資料は `<source>` タグで区切り、資料内の命令文はデータとして扱うよう明示する（プロンプトインジェクション対策の一部。完全な防御ではない）。
- **決定的な根拠検査**（`agents.check_grounding`）では、`source_ids` のない主張と、提供されていない資料の引用を検出する。1件でもあれば `needs_review` とする。
- 出力は常に提案（`proposals`）として保存し、公開・承認経路は存在しない。
- 限界: 引用元の資料IDが正しくても、内容が資料と一致しているか（引用の忠実性）は検査していない。次工程の課題。

## 4. 常時稼働の考え方

33機能ぶんのモデルを常時推論させる必要はない。**33機能は常にジョブを受け付け、推論はジョブが来たときだけ行う。**

- Worker×N（既定2）がキューをポーリングし、ジョブがあれば実行する
- Monitor（5秒周期）がリース回収、外部アンカーの更新、監査検証（既定300秒）を行う
- 日次の呼出上限（既定200）と費用上限（既定0 USD）を設ける。**単価が未設定の外部モデルは「費用を管理できない」として拒否する**
- `health` コマンドの終了コード: 0=正常 / 1=劣化 / 2=停止中 / 3=監査異常。監視ツールやタスクスケジューラから利用できる

## 5. 画面構成（バランス型の情報密度 + アイコン中心）

| 画面 | 内容 |
|---|---|
| ホーム | 状態別件数、6本部のアイコンカード（33機能のドット: 処理中・Hold・Signal限定を区別）、最新の成果、異常通知 |
| 組織 | 本部タブ → 機能タイル（未照合・Signal限定バッジ）→ 詳細（承認権限は「なし（未照合）」と表示） |
| 連携図 | 総合・統括を中心に、委員会・G1〜G5、6本部、33機能を同心円で表示（未照合の関係は点線） |
| AI対話 | 機能・プロバイダ・モデル・区分・根拠資料を選択。処理過程（受付→実行→根拠検査→下書き/要確認）と根拠IDを表示。出力は文字・音声・両方から選択 |
| ジョブ | 一時停止・再開・中止・Hold解除、試行回数、Hold理由 |
| 監査 | 即時検証、監査ログ閲覧（auditor 権限が必要）、停止中の再開 |

音声について:

- **音声出力**は `speechSynthesis` を使う。多くの環境では端末内で合成されるが、ブラウザとOSによってはクラウド音声を使う可能性がある（**未検証**）。
- **音声入力**は**既定で無効**にしている。`Permissions-Policy: microphone=()` でマイクを遮断し、ボタンも無効化している。Chrome の Web Speech API は音声をクラウドへ送る実装のため、未公開の取材内容が外部へ送られる恐れがある。有効化には `settings.json` の `voice_input_enabled: true` が必要で、これは運用判断の対象とする。端末内で動く音声認識（例: whisper.cpp）への置き換えは次工程とする。
